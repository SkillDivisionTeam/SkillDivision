## 3. Цели дизайна

### 3.1. Требования пользователя

#### Требования заказчика и конечных пользователей

Проект «Skill Division» разрабатывается по заказу корпоративных структур, заинтересованных во внедрении интерактивной платформы для вовлечения сотрудников через игровые механики, квизы и аналитику активности. Требования были сформулированы как со стороны заказчика, так и со стороны конечных пользователей.

#### 3.1.1. Требования заказчика

- Создание универсальной системы геймификации для внутренних мероприятий компании.
- Поддержка Telegram-бота как основного канала взаимодействия участников.
- Наличие веб-интерфейса для HR-специалистов с аналитикой, отчетами и настройками квизов.
- Возможность сегментации сотрудников по отделам и проектным группам.
- Реализация системы мотивации и рейтингов для повышения вовлеченности персонала.
- Поддержка экспорта данных в форматы CSV/Excel для внутренней отчетности.
- Встроенные инструменты аналитики и визуализации результатов мероприятий.
- Интеграция с ИИ-модулем для автоматической генерации вопросов по заданной теме.
- Обеспечение конфиденциальности данных и соответствие требованиям законодательства РФ.
- Возможность развертывания решения на корпоративных серверах или в облаке.

#### 3.1.2. Требования конечных пользователей

**Участники (игроки)**

- Простая регистрация через Telegram-бот.
- Участие в квизах и командных соревнованиях.
- Отображение результатов, рейтинга и достижений.
- Получение уведомлений о новых мероприятиях.
- Удобный, понятный интерфейс без необходимости обучения.
- Гарантированная защита персональных данных.

**Организаторы (HR, тимлиды)**

- Доступ к панели управления для создания и редактирования квизов.
- Возможность просматривать аналитику: количество участников, точность ответов, активность по отделам.
- Получение автоматических отчетов и экспорт данных.
- Настройка уровней сложности и тематики мероприятий.
- Возможность использования ИИ для генерации новых вопросов.

**Администраторы системы**

- Поддержка централизованного управления пользователями и контентом.
- Возможность модерации контента и блокировки пользователей при нарушениях.
- Мониторинг состояния серверов и резервное копирование данных.
- Настройка безопасности, прав доступа и логирования событий.
- Поддержка обновлений и масштабирования системы без прерывания работы.

Таким образом, требования заказчика определяют цели и приоритеты проекта с точки зрения бизнеса, а требования конечных пользователей — конкретные функции и удобство использования системы на практике.

## 4. Исключенные возможности и неподдерживаемые сценарии

В рамках текущего релиза проекта «Skill Division» (версия MVP 1) часть потенциальных возможностей была сознательно исключена из реализации по соображениям сроков, бюджета и приоритетов. Ниже приведен перечень исключенных и временно неподдерживаемых функций с обоснованием.

### 4.1. Исключенные функциональные возможности

#### 4.1.1. Мобильное приложение (Android/iOS)

- **Обоснование:** основное взаимодействие реализуется через Telegram-бот, что обеспечивает кроссплатформенность без необходимости отдельной мобильной разработки.
- **Возможное включение:** рассматривается в будущих релизах при наличии стабильной пользовательской базы.

#### 4.1.2. Голосовое и видео-взаимодействие в квизах

- **Обоснование:** внедрение аудио/видео-потоков усложняет архитектуру и требует дополнительных серверных мощностей.
- **Возможное включение:** планируется рассмотреть на этапе масштабирования проекта (версия 2.0).

#### 4.1.3. Интеграция с внешними HRM/ERP-системами (например, SAP, 1C)

- **Обоснование:** MVP не требует интеграции с корпоративными системами, основной акцент на автономной работе.
- **Возможное включение:** при выходе проекта в корпоративное использование.

#### 4.1.4. Система внутриигровых вознаграждений (баллы, подарки, купоны)

- **Обоснование:** механика наград не является приоритетом для тестирования MVP.
- **Возможное включение:** будет добавлена при переходе к стадии монетизации.

#### 4.1.5. Поддержка офлайн-режима работы

- **Обоснование:** решение базируется на онлайн-сервисах (Telegram API, серверная аналитика) и требует постоянного подключения к сети.
- **Возможное включение:** не планируется, так как офлайн-режим противоречит концепции проекта.

#### 4.1.6. Возможность кастомизации интерфейса пользователем

- **Обоснование:** на этапе MVP реализуется единый корпоративный стиль. Индивидуальные темы оформления не требуются.
- **Возможное включение:** возможно внедрение при выпуске версии с white-label функциональностью для корпоративных клиентов.

### 4.2. Неподдерживаемые аппаратные и программные сценарии

#### 4.2.1. Устройства с устаревшими операционными системами

- Не поддерживаются устройства с Android ниже 14 и iOS ниже 19, а также Windows ниже версии 10.
- **Обоснование:** обеспечение совместимости с устаревшими платформами повышает затраты и снижает производительность.

#### 4.2.2. Работа без подключения к интернету

- **Обоснование:** все взаимодействие с сервером, Telegram API и системой аналитики требует постоянного интернет-доступа.

#### 4.2.3. Использование сторонних Telegram-клиентов

- **Обоснование:** стабильная работа гарантируется только при взаимодействии с официальным клиентом Telegram.

### 4.3. Перспективы включения исключенных возможностей

| Версия | Планируемый срок | Функциональность |
| ------ | ---------------- | ---------------- |
| 2.0 | до конца 2026 г. | Интеграция с HR-системами, добавление наград и баллов, усовершенствование аналитики |

Таким образом, текущий релиз сосредоточен на стабильной работе основных функций: проведении квизов через Telegram-бот, управлении мероприятиями через веб-интерфейс и сборе аналитических данных. Остальные функции будут реализованы поэтапно в соответствии с планом развития проекта.

## 5. Предположения и зависимости

В ходе разработки функциональной спецификации проекта «Skill Division» были определены ключевые предположения и зависимости, влияющие на реализацию, тестирование и эксплуатацию системы. Эти факторы отражают условия, при которых проект может быть успешно выполнен и внедрен.

### Предположения

- Все участники мероприятий имеют стабильный доступ к интернету и возможность использовать официальный клиент Telegram.
- Пользователи (участники, организаторы и HR-специалисты) обладают базовыми навыками работы с мессенджерами и веб-приложениями.
- Организаторы предоставляют достоверные данные о мероприятиях (темы, расписание, описание), необходимые для настройки бота и аналитики.
- Минимум 50% участников согласятся на обработку персональных данных для аналитических целей и генерации HR-отчетов.
- Telegram-бот и веб-приложение будут синхронизироваться с сервером в реальном времени с задержкой не более 5 секунд.
- ИИ-модели (например, Yandex GPT или GigaChat) смогут корректно генерировать вопросы для квизов при корректной настройке промптов.
- Первые тестирования проекта будут проведены на мероприятиях с числом участников до 100 человек.
- Пользователи будут использовать современные версии браузеров (Chrome, Edge, Firefox) для работы с веб-интерфейсом.

### Зависимости

- Работа Telegram-бота напрямую зависит от стабильности и доступности Telegram API.
- Веб-приложение зависит от корректного функционирования REST API и серверной инфраструктуры Django.
- Доступность аналитических функций зависит от корректной работы базы данных PostgreSQL и механизмов выгрузки CSV.
- Производительность и скорость отклика системы зависят от хостинг-платформы (PythonAnywhere или аналогичной облачной среды).
- Корректность ИИ-генерации вопросов зависит от доступности внешних API моделей искусственного интеллекта.
- Правильная работа всех компонентов требует соблюдения политик безопасности и конфиденциальности данных (шифрование, аутентификация).
- Взаимосвязь между Telegram-ботом и веб-интерфейсом должна поддерживаться через единый сервер и общую базу данных.

Таким образом, успешная реализация проекта возможна при соблюдении указанных предположений и обеспечении устойчивости всех зависимых компонентов инфраструктуры.

## 6. Проект решения

### 6.1. Концептуальный проект

Система Skill Division предназначена для проведения интерактивных квизов и оценки участников мероприятий. Решение состоит из двух пользовательских интерфейсов и единого централизованного сервера.

**Основные компоненты системы:**

- **Telegram-бот** — клиент для участников (регистрация, игра, профиль).
- **Веб-интерфейс** — клиент для организаторов (управление, аналитика).
- **Серверная часть (Backend)** — API, бизнес-логика, интеграция с AI.
- **База данных** — хранилище данных.

Архитектура решения основана на модели клиент–сервер и реализуется по паттерну MVC (Model–View–Controller). Telegram-бот и веб-интерфейс являются клиентами, а сервер — точкой взаимодействия и обработки данных.

**Основные акторы системы:**

- **Участник** — проходит регистрацию, участвует в мероприятии, просматривает свои результаты.
- **Организатор** — создаёт мероприятия, формирует квизы и управляет процессом проведения.
- **HR-специалист** — анализирует результаты участников и выгружает отчёты.

**Основные сценарии использования системы:**

1. Организатор создает мероприятие с помощью Веб-интерфейса.
2. Организатор генерирует вопросы через AI или добавляет вручную.
3. Участник регистрируется через Telegram-бота (`/start`).
4. Участник играет в Квиз или Дуэль.
5. Система сохраняет баллы и обновляет Лидерборд.
6. HR скачивает отчет или смотрит аналитику онлайн.

### 6.2. Логический проект

Логический проект представляет собой абстрактную модель системы, не зависящую от конкретных технологий. Он описывает внутреннюю структуру будущего решения: объекты, их атрибуты, связи и поведение.

**Основные логические подсистемы:**

1. **Подсистема взаимодействия с пользователем (UI):** включает Telegram-бот и веб-панель администратора. Отвечает за прием и отображение информации пользователям.
2. **Подсистема бизнес-логики:** обрабатывает пользовательские запросы, управляет сценариями регистрации, прохождения квиза, расчета результатов и формирования отчетов.
3. **Подсистема управления мероприятиями:** обеспечивает CRUD-операции с мероприятиями, вопросами и результатами.
4. **Подсистема аналитики:** собирает статистику, формирует рейтинги, экспортирует результаты.
5. **Подсистема данных:** управляет хранением информации и связями между объектами системы.

#### Диаграмма классов

Пример описания сущностей:

| Сущность | Атрибуты | Описание |
| -------- | -------- | -------- |
| `User` | `id`, `username`, `tg_id` | Пользователь системы (участник, организатор, HR) |
| `Profile` | `user_id`, `role`, `avatar` | Профиль пользователя с ролью и аватаром |
| `Event` | `id`, `title`, `date`, `event_code`, `is_active` | Мероприятие, включающее один или несколько квизов |
| `Question` | `id`, `event_id`, `text`, `options` (JSON), `correct_index` | Вопрос квиза |
| `QuizResult` | `id`, `user_id`, `event_id`, `score`, `created_at` | Результаты прохождения |

**Основные связи:**

- Один пользователь может участвовать в нескольких мероприятиях.
- Одно мероприятие содержит несколько квизов.
- Один квиз содержит множество вопросов.
- Каждый пользователь имеет один или несколько результатов.

### 6.3. Физический проект

Физический проект описывает реализацию решения в терминах технологий, инфраструктуры и средств развертывания.

**Технологический стек:**

| Компонент | Технология |

| Backend | Python 3.11, Django REST Framework |
| Frontend | React, Vite, TypeScript |

| Инфраструктура | Docker, Docker Compose |
| Взаимодействие | REST API |
| Система контроля версий | Git, GitHub |

> [!NOTE]
> Диаграмма развёртывания будет добавлена в раздел `./images/`.

#### Описание развертывания

1. Все модули системы упакованы в Docker-контейнеры.
2. Запуск проекта осуществляется через `docker compose up`, что обеспечивает идентичное окружение на всех этапах: разработка, тестирование, продакшн.
3. Контейнеры связаны общей виртуальной сетью, позволяющей безопасный обмен данными.

#### Контейнеры системы

| Контейнер | Назначение |
| --------- | ---------- |
| `backend` | Django REST API и бизнес-логика |
| `frontend` | React-интерфейс организаторов |
| `bot` | Telegram-бот для участников |
| `db` | База данных PostgreSQL |

#### Аргументация выбора технологий

| Технология | Обоснование |
| ---------- | ----------- |
| **Django** | Быстрое создание REST-сервисов и встроенная ORM |
| **PostgreSQL** | Надежная работа с отношениями и JSON-типами |
| **React** | Современный фреймворк с хорошей интеграцией REST-API |
| **Docker** | Обеспечивает переносимость, стабильность окружения и простоту деплоя |

## 7. Требования к инсталляции и деинсталляции

### 7.1. Требования к окружению

- **ОС:** Windows 10/11, Linux Ubuntu 22.04 или macOS
- **Установленные компоненты:**
  - Docker Engine (версия ≥ 20.10)
  - Docker Compose (версия ≥ 2.15)
- **Свободное место:** не менее 1 ГБ
- **Подключение к интернету:** обязательно

### 7.2. Процесс установки

1. Склонировать репозиторий проекта:

   ```bash
   git clone https://github.com/WholeHorse/SkillDivision
   cd SkillDivision
   ```

2. Создать файл `.env` с настройками окружения (см. [`README.md`](../../README.md)).

3. Выполнить команду:

   ```bash
   docker compose up -d --build
   ```

4. Применить миграции:

   ```bash
   docker compose exec backend python manage.py migrate
   ```

5. Проверить работу:

   - **Web:** <http://localhost:3000>
   - **API:** <http://localhost:8000/api/>
   - **Bot:** команда `/start` в Telegram

### 7.3. Процесс деинсталляции

Остановить контейнеры и удалить данные:

```bash
docker compose down -v
```

> [!WARNING]
> Флаг `-v` удаляет все данные контейнеров. Для сохранения данных используйте `docker compose down` без флага.

### 7.4. Дополнительные рекомендации

- При обновлении версии проекта рекомендуется выполнять полную пересборку контейнеров:

  ```bash
  docker compose build
  ```

- Для production-развёртывания рекомендуется использовать сервер с **2 ГБ RAM** и **10 ГБ** свободного места.
